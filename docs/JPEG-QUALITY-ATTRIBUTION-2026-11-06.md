# JPEG与整页画质失败的归因（2026-11-06）

本轮只诊断，不修改生产代码、不发布。原版SkiaSharp3.119.4，对照当前源码的Sdcb.SimdCodecs.Jpeg1.4.0。

## JPEG：这三组严格失败在编码侧

将原24组16×16均匀色输入分别交给原版和SimdSkia编码，再由两个解码器交叉回读；另加原版显式4:4:4/质量100/Ignore Alpha的一组，排除默认采样不同的干扰。编码前24组物理RGBA字节全部一致。

| 隔离方式 | 结果 |
| --- | --- |
| 固定原版编码文件，换两个解码器 | 24/24逐字节一致，最大差0 |
| 固定SimdSkia编码文件，换两个解码器 | 24/24逐字节一致，最大差0 |
| 原版显式4:4:4编码文件，换两个解码器 | 24/24逐字节一致，最大差0 |
| 两个编码器输出均由原版解码器读回 | 3/24最大通道差2，超过既定门槛1 |
| 原版和本库均指定4:4:4，再用共同解码器 | 仍为同3/24最大差2 |

三例为Opaque/alpha32/erase、Premul/alpha32/erase、Premul/alpha32/raw。统一原版解码后，前者中心RGB为(22,11,5)，本库为(22,11,7)。因此此前“编码→自身解码”的联合日志已经拆开：这些失败不能归因于解码器。

本库JPEG编码直接调用Sdcb.SimdCodecs.Jpeg.JpegEncoder.Encode。当前紧凑RGBA输入经EncodingPixels直通，实测原始输入也相同；数值差异发生在编码结果侧。但JPEG是有损格式，输出不同不能直接认定底包不合规或存在算法错误。具体RGB→YCbCr、DCT/量化/舍入中的哪一步不同，尚未逐层追踪，不能把推测写成已证实根因；本结论也只覆盖这24组样本。

另有一项已确认属于本库默认参数兼容差距：SKBitmap.Encode(Jpeg,100)的原版SOF显示4:2:0，本库JpegCodec.Encode硬编码4:4:4。需要在兼容层修正或提供相应选项，不能归责底包；不过显式统一4:4:4后上述三例仍失败，单改默认采样不能解决它们。先前显式4:4:4性能测试的配置与这一默认入口不同，历史数字不改写。

## 整页：绘制结果，不是JPEG编解码

最近整页工具直接读取scene.rgba原始像素比较，没有先编码JPEG。控件100% CPU对照最大通道差96、RMSE约2.418，门槛为32/2；18组CPU/GPU参考组合均未过原门槛。这与JPEG的2色阶误差是两类独立问题。

已知独立测试显示文字灰度覆盖、字体默认配置/栅格化规则、曲线/圆角/描边和部分变换/裁剪边缘与原版存在差异；Direct2D还有本机GPU与本库CPU精细对照未过的情况。责任主要在本库渲染/适配与后端行为，不能由更换图片编解码包自动解决。整页各区域对总误差的贡献尚未完整拆分，不能把某一个局部差异当作整页唯一根因。
